# Changelog

All notable changes to this project are documented here (Conventional Commits style; versions derive from `v*` git tags via axion-release).

## [Unreleased]

### Added
- **`StreamJoinOperator.join` sugar over two streams** (union design step 2, in-memory half): `StreamJoinOperator.join(left, right, config, joinFunction)` tags both sides into `Envelope`s with the `JoinConfig`'s own key selectors and timestamp extractors (current time when an extractor is absent, matching `StreamJoiner`), merges them through `DataStream.union`, routes by the envelope's join key, and runs the operator — returning a `DataStream<O>`. Because the `keyBy` selector is the envelope's join key itself, the manual path's "envelope key vs keyBy selector mismatch → silent mispairing" failure mode is structurally impossible here. Differential tests pin the sugar's output identical to the hand-built envelope path on the in-memory engine; cross-engine Redis merges use the `env.join` orchestration below.
- **`RedisStreamExecutionEnvironment.join` — Redis-side U3 three-pipeline orchestration** (union design step 2, Redis half): `env.join(joinTopic, left, right, config, joinFunction)` expands the sugar for engines where two independent pipelines cannot merge directly — two producer pipelines tag each side into `Envelope`s and write them as self-describing JSON (side + key + timestamp + payload, each with its runtime type name) onto the join topic via the MQ producer (the join key is the MQ key, so same-key records stay partition-ordered), and one consumer pipeline (`fromMqTopicWithId("join-" + joinTopic, joinTopic, joinTopic + "-join")` → parse → `keyBy(Envelope::getJoinKey)` → the join operator) carries the join semantics and returns `DataStream<O>`. The stable source id (`join-<topic>`) keeps the keyed-state key stable across restarts; the wire codec mirrors the join operator keyed-state mapper convention so a payload decodes exactly as it would after a checkpoint restore. joinTopic is user-given, restricted to `[A-Za-z0-9_.-]+` (it feeds the stable source id); the sugar never deletes the topic (trim/TTL follow MQ retention governance); a second call with the same joinTopic fails fast on the duplicate-source-id guard. Runtime gains `implementation project(':join')` (same category as window/checkpoint/watermark). 10 tests (9 unit + 1 Redis-gated integration) pin wire round-trip, type fidelity, null-key rejection, null/blank/config-validation guards, and the end-to-end three-pipeline orchestration. Landing-point decision (env instance method vs a new bridge module vs exposing env on `DataStream`) and the rejected options are recorded in `docs/Union-DualSource-Design.md` §5.
- **`DataStream.union` dual-source primitive** (union design step 1, `docs/Union-DualSource-Design.md`): `DataStream.union(DataStream<? extends T>)` merges two compatible streams by round-robin interleaving (one element per source in turn, draining whichever outlives the other; source-internal order preserved, cross-source order undefined) — implemented on the in-memory engine as a per-consumption iterator over both record suppliers, preserving per-record timestamps, composable with `map`/`filter`/`keyBy` and reusable per sink. The interface default throws `UnsupportedOperationException` (the Redis engine inherits it as an explicit "use join topic mode" landing point per design option U3); `null` or a non-in-memory operand throws before any consumption.
- **Runnable join-sugar example + 3-step integration guide** (union design step 2 acceptance): `examples/.../join/StreamJoinSugarExample.java` is a no-Redis runnable demo of `StreamJoinOperator.join` over two in-memory streams — an INNER variant (matched pairs only) and a LEFT OUTER variant (each left element emits with a `null` right half up front, then re-emits with its peer when the right side arrives in-window) — with `docs/Join.md` gaining a 「接入三步」 section (build `JoinConfig` → call the sugar → consume the returned `DataStream`). The example is pinned by a deterministic test (`StreamJoinSugarExampleTest`) since the examples package is coverage-gated.
- **Per-record checkpoint barrier** (barrier design v2): a record's body now runs under the store's `fenceLock()` (the checkpoint lock after registration), so a checkpoint triggered mid-record blocks until the record finishes all of its state writes instead of splitting them — `synchronized` is reentrant, so the store's own per-write locking is a no-op inside the fence. The end-of-input `drainAllTimers()` is fenced the same way (timer callbacks also write state).
- **`result` dimension on runtime handle-error metrics** (Metrics-Unification-Design v2): `StreamingMetricsCollector.incHandleError` gains an overload carrying the failed record's resolved delivery outcome (`retry` / `fail` / `dead_letter`, from the runner result or `processingErrorResult`); the starter's Micrometer collector emits it as a `result` tag on `redis_streaming_runtime_handle_error_total`. The legacy tagless counter and the default delegation keep custom collectors source-compatible.
- **Named snapshot sources in the in-memory checkpoint cut** (barrier design P2): `InMemoryCheckpointCoordinator.registerSnapshotSource(name, snapshot, restore)` generalizes registration beyond keyed state stores — both callbacks run under the checkpoint lock, so one checkpoint stays a single consistent cut across stores and sources; duplicate names throw and late registration replays the latest restored snapshot. Watermark states join automatically: pipeline segments built with `assignTimestampsAndWatermarks` (both overloads) register their `WatermarkState` under a generated collision-free `watermark-N` name when a coordinator is present, and the checkpoint payload carries the current watermark and idle flag for restore. Window accumulators joined two days later (next entry).
- **Window accumulators in the in-memory checkpoint cut** (barrier design A② + operator-state lifecycle contract, `docs/InMemory-Operator-State-Lifecycle-Design.md`): each terminal-op consumption (each sink) owns one `OperatorState` — the bucket map is a per-consumption field, lazily registered at first drive under a collision-free generated `window-N` name (an unconsumed terminal op never registers; `registerGeneratedSource(prefix, ...)` generalizes the `watermark-N` skip-numbering). The whole record body of `drive()` and the end-of-input flush run under the coordinator's checkpoint lock (the same per-record fence contract as the keyed path), with the source iterator consumed outside the fence — a blocking source cannot freeze checkpoints between records. The snapshot payload records key / window bounds / lastTimestamp / accumulated contents per non-empty bucket (the incremental path's current fire results, or a raw element copy for `apply`/session buckets; `Trigger` instances are not captured — no snapshot API). Restore is FRESH by default: the payload is kept as a read-only inspection view and never injected into live buckets, because in-memory sources replay their full history and adopting restored buckets would double-count every window.
- **JobSpec secret-reference convention** (Security-Hardening-Design C2): config keys prefixed `secret.` hold references (`env:NAME` / `sys:NAME`) instead of plaintext; `RedisJobLauncher` resolves them into a spec copy before the pipeline factory runs (a spec without secret keys is passed unchanged; missing source fails the deploy naming the key and source, never the value). Scheme-less `secret.*` values pass through with a control-plane warn (advisory convention, no migration). `specHash` masks secret literals (`***`) so its input is never dictionary-attackable material, while references hash verbatim so rebinding `env:A` → `env:B` stays visible to agent drift detection; the audit stream carries only fixed fields and never config content. Secret rotation needs no spec change — re-resolving happens on the next upgrade-triggered redeploy.
- **Config-center at-rest content encryption** (Security-Hardening-Design C1): pluggable `ContentCipher` (encrypt/decrypt, no bundled implementation — key material is the integrator's, typically env/JVM). When installed, dataIds under `securePrefix` (default `secure.`) are stored encrypted in the config hash and its history records (marker-wrapped `enc:v1:`), and every read path (getConfig, history, listener initial dispatch, resync poll) decrypts transparently; pub/sub events stay plaintext (at-rest scope only). Legacy plaintext entries read back as-is — no migration needed; marked entries on cipher-less instances are returned raw with a warning; cipher failures fail the publish before storage (no plaintext fallback) and fail the read loudly. Starter: optional `ContentCipher` bean + `redis-streaming.config.secure-key-prefix`.
- **Dynamic scaling** (P4): `RedisJobClient.scaleParallelism(n)` resizes the job's parallelism at runtime — every live consumer is re-pinned to `partitionId % n == subtaskIndex` via the new MQ-layer `ReassignableMessageConsumer.updatePartitionAssignment` (out-of-assignment partitions release their leases promptly, the new owner picks them up on the next rebalance tick without waiting for the lease TTL), subtasks are added or stopped per pipeline. Keyed state and checkpoints are partition-keyed, so they remain valid across a resize — including restoring a checkpoint written at a different parallelism (verified by integration tests). The resize is exclusive with checkpoint flows (shares the `checkpointing` gate); `diagnostics().liveParallelism` reports the live value.
- **Item-audit anti-fraud demo chain** (`examples/.../streaming/itemaudit/` + `docs/CDC-Item-Audit.md`): MySQL-CDC item feed audited by three gates built on the join/CEP operators — trusted binlog input (simulated connector; production swaps in `MySQLBinlogCDCConnector`), LEFT-OUTER reconciliation of item changes against business transactions (unmatched change → `RECON_MISMATCH`), and CEP behavior bounds (off-hours / quantity-spike / probe-run patterns) — with a log + webhook-slot alert funnel, a runnable no-infra demo (`./gradlew :examples:run -PmainClass=...ItemAuditDemo`) and gate-level unit tests.
- **Idle watermark flush** (RT-M3, opt-in via `RedisRuntimeConfig.watermarkIdleTimeout`): a pipeline that has processed no record for the configured duration (or whose watermark generator called `markIdle()`) flushes its watermark to `MAX_VALUE`, firing all due event-time timers and remaining due windows (windowed operators register a flush hook that drains their Redis-side due sets at `MAX_VALUE`); the next record starts a fresh watermark epoch. The record path is unchanged — while records flow, the per-record drain stays the sole owner of the due set, so trigger semantics (e.g. defer-once close triggers) and the `windowMaxFiresPerRecord` clamp behave exactly as before — with delivery-time event times a quiet pipeline no longer strands its windows forever.
- **`DeliveryGuarantee` declaration surface** (`core` `api.stream`): sinks declare their capability via `StreamSink.deliveryGuarantee()` — plain sinks default to `AT_LEAST_ONCE`; `TwoPhaseCommitSink` and the Redis exactly-once building-block sinks (`RedisAtomicCheckpointListSink`, `RedisIdempotentListSink`, `RedisCheckpointedIdempotentListSink`, `RedisOutboxSink`) declare `EFFECTIVELY_ONCE`.
- **Benchmark module** (`benchmark`, not published / not coverage-gated): MQ produce+consume throughput with p50/p95/p99 end-to-end latency, and `triggerCheckpointNow()` drain+snapshot duration on a live Redis runtime pipeline (`./gradlew :benchmark:run`, `REDIS_URL` / `BENCH_*` env knobs).
- **join/cep operatorization** (phase 1 of `docs/Join-CEP-Operators-Design.md`): `join.operator.StreamJoinOperator` adapts the windowed stream-stream join to a `KeyedProcessFunction` over `join.operator.Envelope` (both sides map into tagged envelopes on one join-input stream; zero engine changes, runs on both engines); `cep.operator.PatternSequenceProcessFunction` runs `PatternSequenceMatcher` per key with a bounded key registry (`maxTrackedKeys`). Operator buffer state stays partition-local (not checkpointed) in this phase; `StreamJoiner` gains explicit `(element, key, timestamp)` overloads as the delegate entry point.
- **join/cep keyed-state durability** (phase 2 of `docs/Join-CEP-Operators-Design.md`): both operators persist their per-key buffers through the new `KeyedProcessFunction.Context.getState(StateDescriptor)` — a default method (throwing `UnsupportedOperationException`, so existing custom contexts are unaffected) wired by both engines (in-memory keyed store, Redis keyed store). Join buffers live as one self-describing JSON document per key (`__operator:join:buffers`, runtime class recorded per element); CEP partial matches hydrate from `__operator:cep:partials` on cache miss via `PatternSequenceMatcher.exportPartialMatches()`/`restorePartialMatches()` (per-step concatenation preserves flat event order). After a failover, pairing resumes from restored state — at-least-once recompute downstream (redelivered envelopes may pair again); `maxStateSize` and retention are now scoped per key (window predicate still guards matching). (The sugar's blocker — a union/dual-source primitive — landed 2026-10-14 together with the in-memory half of the sugar; see the `DataStream.union` and `StreamJoinOperator.join` entries above. The Redis-side U3 orchestration landed the same day — see the `RedisStreamExecutionEnvironment.join` entry.)
- **In-memory engine streaming model** (runtime): `addSource` now streams records through a bounded hand-off queue (256 records in flight) instead of materializing the whole source — an unbounded source no longer accumulates memory and a slow consumer backpressures the source thread. The eager contracts are preserved: `open()` failures and immediate `run()` failures still throw synchronously from `addSource`; a failure after records were delivered rethrows from the terminal operation. Event-time windows now close mid-stream: `keyBy().window()` carries the upstream watermark state, so windows whose end the watermark passed fire (and purge per trigger semantics) before the input ends. `reduce/sum/count/aggregate` accumulate per window instead of retaining raw elements (`apply` and session-merging assigners keep raw elements).

### Changed
- **Self-built `metrics` module removed** (Metrics-Unification-Design v2): `MetricCollector`/`InMemoryMetricCollector`/`MetricRegistry`/`MetricTimer`/`Metric`/`MetricType` and the `prometheus.*` simpleclient bridge are deleted — the module had zero production consumers. Micrometer remains the single observability facade (starter auto-bridges `MqMetrics`/`RedisRuntimeMetrics`/`RateLimitMetrics`/`RetentionMetrics`); Prometheus scraping goes through `micrometer-registry-prometheus` or Spring Boot Actuator. docs/Metrics.md carries the InMemoryMetricCollector → Micrometer migration table; existing `redis_streaming_*` snake-case meter names are unaffected.
- **MQ delivery retry policy renamed** (Dedup-Retry-DLQ-Boundary-Design residual debt): `mq.retry.RetryPolicy` is now `mq.retry.DeliveryRetryPolicy` to kill the same-name-different-type collision with the `reliability.RetryPolicy` config POJO (delivery-layer retry interface vs user/operator-layer retry config). `ExponentialBackoffRetryPolicy` implements the renamed interface; the package is unchanged. **Breaking rename**: implementors re-implement the new name.
- **Runtime metrics SPI publicized** (Metrics-Unification-Design v2): `RedisRuntimeMetricsCollector` is renamed and moved to the common API module as `io.github.cuihairu.redis.streaming.api.metrics.StreamingMetricsCollector` — the single public interface for the runtime's metric vocabulary (jobs, pipelines, handler outcomes, checkpoints, keyed state, watermarks, windows). The `RedisRuntimeMetrics` static facade and the starter's `RedisRuntimeMicrometerCollector` keep their locations and only change the implemented type. **Breaking rename**: custom collectors re-implement the new interface.
- **State unification step 3** (`docs/State-Unification-Design.md`): `RedisStateBackend` is now a thin adapter over the runtime keyed state store — the four standalone state implementations (`RedisValueState`/`RedisMapState`/`RedisListState`/`RedisSetState`) are deleted, and every state created through the backend lands in the standard keyed layout (job-namespace keys registered in the `stateKeys` index and `stateSchema` registry, plain JSON over `StringCodec`, a fixed solo identity pinned around each operation). **Incompatible by design**: keys (`{prefix}:{job}:cg:standalone:topic:standalone:p:0:state:standalone:...`) and codec (no Redisson `@class` type info) differ from the old flat `{keyPrefix}{name}` layout, so old data is not read — docs/state.md carries the migration table and a read-old-then-rewrite recipe; the standalone constructor changes from `(redisson, keyPrefix)` to `(redisson, jobName[, stateKeyPrefix])`.
- **Redis runtime event-time timer overflow now fails the record** (RT-M2): `Context.registerEventTimeTimer` throws `IllegalStateException` when the queue is at `eventTimeTimerMaxSize` instead of silently dropping the registration — a dropped timer strands its window/callback forever, which was silent wrong results. The record now flows through the standard `processingErrorResult` path (default `RETRY`, DLQ after retries) with `incHandleError` metrics and the runtime error annotation headers, so saturation is visible and recoverable (drain the queue or raise the cap); `0` (= unlimited) and the below-capacity path are unchanged. The throttled overflow warning is removed along with the silent drop it described.
- **docs site dependency vulnerability pins**: npm `overrides` in `docs/package.json` pin patched versions of the three open Dependabot alerts in the docs build graph — `source-map-js@1.2.2` (#96), `vue`/`@vue/server-renderer@3.5.43` (#95), `katex@0.18.2` (#97). - **Redis runtime rejects forked pipelines sharing a consumer group** (RT-M7): `RedisStreamExecutionEnvironment.registerPipelineDefinition` now throws `IllegalStateException` when a second pipeline registers the same `(topic, consumerGroup)` pair — Redis Streams consumer groups distribute each message to a single member, so two pipelines sharing a group silently split the stream between them instead of each reading every message, and chains forked from one source builder would additionally collide on keyed-state names. ### Fixed
- **Keyed list state `update`/`addAll` are atomic** (B-38 parity with the retired standalone list): the keyed `ListState` replacement was clear + per-element add and appends were per-element — a dropped connection mid-way left a half-replaced or partially appended list, and a retry re-appended duplicates. Both now run as a single `REDIS_WRITE_ATOMIC` batch (`update` = DEL + addAll in one MULTI/EXEC, empty update = DEL only; `addAll` = one addAll batch), with the `stateKeys` checkpoint index and schema registration preserved on the batch paths; pinned in `RedisKeyedListStateGapClosureTest`.
- **KTable changelog ordering**: back-to-back `RedisKTable.put()` calls could emit changelog events out of order — the MQ producer runs each send on a shared async pool, so a delete could be XADDed before the put it deletes and a full-history `toStream(env)` replay would reconstruct the wrong value. Changelog emits are now chained per table so the topic receives events in `put()` call order, while `put()` stays non-blocking and best-effort (a failed emit only warns and never drops later events).
- **Redis runtime state restore** (RT-M4): restore is now stage-then-RENAME instead of delete-then-rebuild — snapshot keys are written under `<finalKey>:rst:<checkpointId>` staging names first, then atomically swapped into place per key; any staging or swap failure cleans up the staging keys and throws (the live state is never deleted up front), and empty snapshot entries clear their live key only after the swap succeeded. **Behavior change:** an explicitly requested restore that fails now aborts the job start (`IllegalStateException`) instead of silently continuing without the restored state — a checkpoint from a different `jobName` and "no checkpoint yet" still start fresh.
- **Redis runtime windows** (RT-H3): a failed sink emit during a window fire no longer destroys the window. The five windowed operators (reduce/aggregate/apply/sum/count) purge accumulated state only after a successful emit, and `fireDueWindows` re-queues a fired member at its close score when the emit throws — the redelivered message re-fires the complete window instead of silently losing everything accumulated before the failure (apply previously purged even before emitting its buffered results).
- **spring-boot-starter**: logback pinned to 1.4.14 (1.5.x removed `LoggerContext.getConfigurationLock()` which Spring Boot 3.2's logging system requires).
- **spring-boot-starter**: empty default `redis-streaming.redis.password` no longer sends an `AUTH` command (broke servers without a password).
- **spring-boot-starter**: `MqHealthIndicator` bean moved to a class-level `@ConditionalOnClass` nested configuration (actuator is optional; method-level guards did not prevent return-type introspection). Micrometer collector/installer beans gained `@ConditionalOnBean` guards so the starter now boots without actuator/MeterRegistry.
- Redis engine: a consumer failing to `resume()` after a checkpoint left the remaining consumers paused indefinitely.
