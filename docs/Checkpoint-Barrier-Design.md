# SourceContext.getCheckpointLock's Real Wiring and the Checkpoint Barrier Protocol Boundary

This page is for review and contains no code changes. Goal: `SourceContext.getCheckpointLock()` is currently a dead contract (the only production holder is the engine itself; no snapshot side ever synchronizes on this lock); clarify both engines' checkpoint models, give the minimal path to making the lock semantics real, and assess where a Flink-style cross-operator barrier protocol would genuinely pay off on the Redis engine.

> Landing status: P1's snapshot barrier landed 2026-10-11, P2's registration-surface generalization landed 2026-10-12, the per-record barrier landed 2026-10-13, and window accumulator registration landed 2026-10-14 (see Approach A's ① ② and the landing records); A③'s Redis unaligned v2 review verdict issued 2026-10-14 (right direction, not implemented in that batch, split into its own batch — see Approach A ③'s review verdict), and its prerequisite first step, the CAS gate's two-level split, landed the same day (see Approach A ③'s landing note). The "Current State" below is the pre-landing fact inventory; where it differs from today's code, the landing records win.

## Current State (fact inventory)

### SourceContext: contract and implementation

- Contract: the nested interface in `core/.../api/stream/StreamSource.java` L57-82 — `collect/collectWithTimestamp/getCheckpointLock/isStopped`.
- The only production implementation: the in-memory engine's `runtime/.../StreamExecutionEnvironment.addSource` (L89-125). `emit` (L226-240) does `queue.put` inside that lock (since 07539c7); the consumer thread never takes the lock (preventing backpressure deadlock).
- **No snapshot side synchronizes on this lock**: `InMemoryCheckpointCoordinator.triggerCheckpoint` (internal, a single-monitor `synchronized`) directly copies the registered stores' snapshots without taking the source lock; the Redis engine has no SourceContext at all — its "source" is the MQ consumer group (`fromMqTopic*`), with records entering `RedisPipelineRunner.handle` on MQ consumer threads.
- None of the 5 `StreamSource` implementations (CDCSource/CollectionSource/FileSource/GeneratorSource/RedisStreamSource) calls `getCheckpointLock()`; outside tests the whole repo has no callers.

### The Two Engines' Checkpoint Models

| Dimension | in-memory engine | Redis engine |
| --- | --- | --- |
| Coordinator | `InMemoryCheckpointCoordinator` (registers only `InMemoryKeyedStateStore`) | `RedisRuntimeCheckpointManager` (uses `RedisCheckpointStorage` directly, not via `RedisCheckpointCoordinator`) |
| Trigger | manual `triggerCheckpoint()`, no scheduling | the `checkpointInterval` period (leader only) / `triggerCheckpointNow()` |
| Quiescing | **none** — snapshots race the pipeline threads | stop-the-world: pause all consumers → drain until `inFlightBarrier()==0` (30s cap by default) |
| Snapshot content | `HashMap` copies of the registered stores | offsets (the commit frontier or the defer-ack override) + the current values of every Redis key in the stateKeys index + schema + the 2PC handles |
| Consistency | **tearing risk**: while a consumer thread updates `InMemoryKeyedStateStore` inside an operator (holding no lock), a third thread's snapshot can see intermediate states (CME/dirty reads) | pause+drain guarantees no fetched-but-unaccounted records; the defer-ack freeze + 2PC preCommit/commit/markSinkCommitted chain is verified end to end |

The `checkpoint` module's `RedisCheckpointCoordinator` is an **ack-counting** coordinator (the pending table is in-process; gathering `requiredTaskAcks` auto-completes), and neither runtime side uses it; the repo's only "barrier" concept is the MQ layer's `inFlightBarrier()` (a consumer-side in-flight view serving pause+drain, not a dataflow barrier). `docs/Deployment.md:97` already records this faithfully: "checkpointing is single-process stop-the-world (no cross-instance barrier)".

## Problems

- `getCheckpointLock()` is a dead contract: the engine builds the lock and nobody uses it. A user following the Flink habit of taking the lock to spin-protect an external resource gets no guarantee whatsoever; the documentation has to admit "the lock currently only guards enqueueing".
- In-memory checkpoints genuinely tear: `triggerCheckpoint` has no happens-before with consumer threads' operator-state updates. Today it is only usable with "the pipeline is already stopped", a precondition nothing enforces — the API shape invites misuse.
- The Redis engine's stop-the-world cost: throughput drops to zero during checkpoints; the pause poll granularity starts at 50ms; shrinking `checkpointInterval` amplifies the pause frequency, growing it worsens RPO. defer-ack/2PC mitigate correctness, not the quiescing cost.
- The barrier protocol's real constraints: the Redis engine has **no queues between operators** (`RedisOperatorNode.process` is a single-threaded chain), so on paper "aligned barriers" and pause+drain are mathematically equivalent at single parallelism — what a barrier could buy here is not alignment but **not stopping consumption**.

## Candidate Approaches

### Approach A: Make the lock semantics real (small steps) + keep stop-the-world as the default + unaligned barriers as an optional v2 (recommended)

Reasons: ① fixes a real defect on an already-verified model; ② Redis state is already an external current-value store (a snapshot = a copy, not serializing operator heaps), so async snapshots have inherently low payoff and full barrier machinery would be high-effort/low-reward; ③ v2 is only worth it where "stopping consumption is unacceptable".

**① The in-memory snapshot barrier (P1, landed 2026-10-11)**: the landing corrected this document's initial plan — "consumers hold the lock per record" would deadlock: when a user wraps `collect()` in `getCheckpointLock()` (the Flink habit), the producer can block on a full queue while holding that lock; if the consumer's state writes also needed the same lock, the queue would never drain. The real barrier is therefore a **two-lock contract**: the coordinator adds `checkpointLock()` (an independent monitor), on which all mutations of registered stores (put/remove/setCurrentKey/snapshot/restore) and the coordinator's snapshot/restore synchronize, and `triggerCheckpoint` holds it across all stores → one checkpoint is a single consistent cut, tearing (CME/dirty copies) eliminated; the lock is held only over bounded non-blocking in-memory operations. `SourceContext.getCheckpointLock()` keeps returning the source-level emission lock (producers may hold it across a full queue; consumers never take it) — the two locks never intersect, so backpressure never deadlocks. The per-record barrier landed 2026-10-13: the record body executes wholly inside the store's `fenceLock()` (= the registered `checkpointLock`), so a checkpoint triggered mid-record blocks until the record has written all its state and no longer splits a single record's multiple writes; `synchronized` is reentrant, so the store's own per-write locking idles inside the fence. After window accumulator registration (②) the bucket table's snapshot is naturally atomic. Tests pin it: snapshots during locked writes must wait and see the written value, concurrent writes + 200 rapid snapshots with zero tearing, and 20 000 records through a live pipeline with concurrent checkpoints and zero loss.

**② registerStore generalization (P2, landed 2026-10-12)**: the registration surface generalized from `registerStore(InMemoryKeyedStateStore)` to `registerSnapshotSource(name, snapshot, restore)` — any `(name, snapshot, restore)` triple can enter the checkpoint cut, protected by ①'s lock exactly like the keyed stores; duplicate names are rejected, and `latestRestoredStateByStoreId`'s deferred-restore semantics apply to snapshot sources too. `WatermarkState` gained a `Snapshot(watermark, idle)` payload plus `snapshot/restoreSnapshot`, and both `assignTimestampsAndWatermarks` overloads auto-register under a collision-free generated `watermark-N` name on the coordinator-holding pipeline segment (name collisions skip numbers). **Window accumulators registered 2026-10-14** (the contract in docs/InMemory-Operator-State-Lifecycle-Design.md, implemented per recommendations D1-a/D2-a/D3-a/D4-a/D5-a/D6-a): each terminal-operator consumer holds one piece of operator state — the bucket table was promoted from a drive() local to a field of that instance, lazily registered under a collision-free `window-N` name when consumption starts (unconsumed terminal operators register nothing); the drive() loop body and end-of-input flush run wholly inside `fenceLock()` (= the coordinator's checkpoint lock, the same contract as the keyed path's per-record barrier; source iteration stays outside the fence — a blocking source must not freeze checkpoints); snapshot payloads record per bucket key/window boundaries/lastTimestamp/accumulated contents (the incremental path's current fire result or a copy of the raw elements), Triggers have no snapshot API and instances do not enter the snapshot; restore defaults to FRESH — payloads only write a read-only checkpoint mirror and never inject live buckets, in-memory sources replay in full, and adopting restored buckets would double-count (D3's correctness trap is closed at the contract level); no deregistration API — a finished run's window state stays in later checkpoint cuts (the final state of that run).

**③ The Redis engine's v2 unaligned checkpoints (review verdict issued 2026-10-14)**: do not stop consumption; the epoch freeze point shrinks from "full drain" to "2PC preCommit + defer-ack freeze" (neither of which needs to pause the world anyway) — offsets already exist under the defer-ack snapshot semantics; keyed state takes Redis's current values + a snapshot version, and recovery dedups by "replay only records with id > snapshot frontier" (idempotent sink keys already exist). Two prerequisites: the `checkpointing` CAS gate shared with `scaleParallelism` must split into two levels (rescaling still needs full silence; checkpoints no longer do), and preCommit epochs must align across parallelism. The risk concentrates in the 2PC interaction; the benefit accrues only to long `checkpointDrainTimeout`/high-throughput jobs; not enabled by default.

> **Review verdict (2026-10-14, patrol proxy decision)**: right direction, **not implemented in that batch**. The sketch is self-consistent — preCommit + defer-ack freeze is a minimal consistency point, offsets reuse the existing defer-ack snapshot semantics, and taking keyed state's current values + a version with frontier-based replay dedup all hold; but it is a correctness-critical path with a narrow benefit surface (perceptible only for long `checkpointDrainTimeout`/high-throughput jobs), and its prerequisites are two hard pieces: the two-level split of the `checkpointing` CAS gate shared with `scaleParallelism`, and multi-parallelism preCommit epoch alignment. **Recommendation: split into its own batch, off by default** (a new `RedisRuntimeConfig` switch); landing order: first the CAS gate's two-level split (independently testable, also beneficial to the existing aligned path), then evaluate epoch alignment and frontier dedup; the 2PC interaction is the main risk and needs dedicated integration tests. That batch changed no code.
>
> **Landing note (2026-10-14, the P1014B batch)**: the first step of that landing order has been executed — the original single `AtomicBoolean checkpointing` was refactored into `runtime/redis/internal/CheckpointGate`, a two-level gate (a serialization level: at most one control operation at a time; a full-silence level: consumers paused/in-flight quiesced). Aligned checkpoints (periodic and manual) and `scaleParallelism` still take both levels (serialization first, then full silence, released in reverse; the class invariant `fullSilence ⇒ serialization` guarantees no deadlock), and **behavior is point-for-point identical with the pre-split gate** — the original gate's three holder classes were already pairwise exclusive, and the split merely makes "mutual exclusion" and "full silence" explicit, leaving a future unaligned checkpoint the entry of "take only the serialization level, never stop consumption". The diagnostics `checkpointing` key became the serialization view and a new `fullSilence` key was added. The gate's lattice is pinned by `CheckpointGateTest`'s 4 tests: checkpoint/rescale mutual exclusion, a second begin refused, a refused begin leaving no residue on the serialization level (an anti-starvation invariant), and 4 threads × 2000 contentions with zero overlap. The second step's evaluation is in the next section, "epoch alignment and frontier dedup assessment".

#### Epoch Alignment and Frontier Dedup Assessment (2026-10-14, the P1014B batch)

A code walkthrough (grounded in `runtime/.../redis/RedisStreamExecutionEnvironment`, `.../internal/RedisRuntimeCheckpointManager`, and `mq/.../impl/RedisMessageConsumer`) found four premises of the sketch at odds with reality; corrections first:

1. **Pause and drain are best-effort, and the drain timeout proceeds anyway**. `RedisRuntimeCheckpointManager.triggerCheckpoint` itself is pure snapshot+store with no pause/drain/2PC; the orchestration lives entirely in `RedisStreamExecutionEnvironment.triggerCheckpointWhilePaused` — pause **all** consumers first, then poll `Σ inFlightBarrier()==0` up to `checkpointDrainTimeout` (default 30s), and **on timeout only `log.warn` and continue as usual** (no abort, no failure). Today's correctness relies not on "silence" but on the 2PC abort/recover path backstopping the in-flight records under a drained-timeout.
2. **Snapshot atomicity is single-Lua-call level, not job-level**. The whole pipeline's offsets and state are written in one Lua transaction under one checkpoint id and one `timestamp`, but semantically the job does not get a single consistent cut: the `stateKeys` SCAN happens **before and outside** the Lua, so the snapshot reads Redis's current values (plus the `stateSchema` strings), not "operator state at one instant".
3. **"Keyed state = current values + a snapshot version" does not hold**. `meta` carries only `jobName/jobInstanceId/stateKeyPrefix/sinkCommitted/fencingToken`, with no per-partition/per-key version fields, so "restore replays only ids > frontier" has nothing to hang on — restored keyed state is a wholesale keyspace **copy-overwrite** (a staging name + an atomic `RENAME` flip), no delta, no replay semantics.
4. **"Offsets reuse the existing defer-ack snapshot semantics" holds only under `deferAckUntilCheckpoint=true` (default false)**. The default path reads the **commit frontier hash** (the maximum **acked** id), reading neither `last-delivered-id` nor the PEL; in defer-ack mode it stores the maximum id recorded under that mode.

**Conclusions on the two open questions**

- **Frontier dedup already exists today — the aligned path's recovery semantics is already "rewind to the frontier and replay" (2026-10-15 erratum: this item's first draft said "only the two pipeline segments are missing", contradicting the facts stated in the same sentence; a drafting slip)**. Those two segments are not a gap but the existing implementation: the snapshot already **explicitly serializes** the per-partition frontier into its payload (`snapshotOffsets` writes `SNAPSHOT_KEY_OFFSETS`, storing Stream ids per partition as `(topic, cg, pid) → "ms-seq"`, the defer-ack max id or the commit frontier), and restore already reads them back as the consumption start (`restoreFromCheckpoint → restoreOffsets` rebuilds the group on the frontier via `XGROUP DESTROY + XGROUP CREATE`, after which `XREADGROUP >` only delivers `id > frontier`). Note this is **not** a consumer-layer `id <= frontier` filter (the consumption layer has no id filtering; the skip is implicit in the group boundary, and the PEL is discarded with it); restore = "snapshot state + rewind to the frontier and replay", whose correctness premise is "records with effect ≤ frontier have all their effects inside the snapshot" — the aligned path satisfies this barely, via fullSilence (best-effort, item 1 above) + the 2PC backstop; and that is exactly the property unaligned wants to avoid.
- **Multi-parallelism epoch alignment: infeasible under the current snapshot structure; not a small change**. The checkpoint id is a per-env-instance JVM `AtomicLong` (not Redis-assigned, not per-subtask); the snapshot is one global Lua write and can only represent one global instant; there is no per-partition effect fence and no epoch traveling with records. The existing `inFlightBarrier()` (`inFlight + readsInFlight`, already fixed for the "called inside the pause window" race) is a consumer-**local** view — not per-partition, not probeable across instances, no substitute for a cross-subtask barrier. To be unaligned and correct, one must add a **Redis-visible per-partition in-flight/effect fence** (incr before each subtask processes partition p, decr after its ack decision, the coordinator waits for `inFlight(p)==0` across all subtasks) and split the snapshot Lua per partition.

**A③'s core premise ("epochs can align") therefore does not hold**: there is no epoch to align today; doing frontier dedup without a per-partition effect fence degrades into "rewind and replay", losing exactly the cross-cut records the design wanted to avoid pausing for (their effects land after the snapshot while their ids sit inside the frontier — no version field to judge, no replay to make up).

**Recommendation (for the next batch's decision)**

- The minimal consistency point of unaligned should be redefined as **per-partition barriers + per-partition snapshot cuts + exclusive replay during recovery**, not "preCommit + defer-ack freeze". (2026-10-15 erratum: the first draft here claimed "the frontier three segments can land independently, without epoch alignment, as pure plumbing" — that does not hold. Frontier serialization and recovery-time seek already exist (see the frontier-dedup item); there is no independently landable "frontier trio"; "recovery-time exclusivity" depends on a job-level global gate, i.e. defect (2) below, and is not pure plumbing either. The only genuinely missing primitive is the per-partition effect fence + splitting the snapshot Lua per partition.) The decision therefore reduces to a choice: **design and build the fence** (its own design batch; a new MQ-layer primitive with the 2PC interaction as the main risk, requiring dedicated review + integration tests), or **keep aligned checkpoints as the only consistent path**. There is no cheap middle path that avoids the fence.
- The per-partition fence is a new MQ-layer primitive (the 2PC interaction its main risk) and needs its own design; until then **aligned checkpoints remain the only consistent path**, and if unaligned must go first it can only be positioned as "best-effort with RPO > 0", stated explicitly in the API and docs.
- Also recorded: three pre-existing defects found incidentally in that batch (outside A③'s scope, **not entered into todo**, for deciding whether to scope them): (1) `triggerCheckpoint` never calls `renewLeadership()` — a leader that lost its lease can still write snapshots → unfenced orphan snapshots; (2) the control gate is per-env-instance rather than a job-level global lock — two `LaunchedJobClient`s of the same job name can snapshot in parallel (leader election only coordinates periodic triggering and does not protect manual `triggerCheckpointNow`); (3) `DeferredAcks` has a drain-and-ack convenience overload with no production callers (`ackAll(client, keys)`) that acks unconditionally outside the frozen set with no synchronization against "checkpoint completed" — called outside the checkpoint flow, it would credit the next epoch's ids into the commit frontier early. **Disposition (2026-10-15, patrol proxy decision, all three scoped)**: (1) fixed — a renew-before-store gate: an instance that once held the lease but failed to renew refuses to write snapshots (returns null, nothing persisted; the never-held-lease follower manual path is preserved; pinned by `RedisRuntimeCheckpointManagerLeadershipGateTest`'s 4 tests + `RedisLeaderElectionIntegrationTest` integration); (3) fixed — the caller-less drain-and-ack overload is deleted, the only ack surface narrowed to "frozen snapshot + checkpoint-success path" (`ackAll(client, frozenSnapshot, keys)`, the 3 related DeferredAcks test classes updated); (2) fixed — the job-level control gate landed: `runtime/redis/internal/JobControlGate`, a two-level Redis lease gate (`ctl:excl`/`ctl:silence`, TTL self-healing + Lua CAS release + refusal when Redis is unreachable), wired into `triggerCheckpointInternal` and `scaleParallelism`, toggled with `leaderElectionEnabled` (`jobControlGateEnabled` can override either way, `controlGateWait` defaults to fail-fast), pinned by `JobControlGateIntegrationTest` integration (dual-client mutual exclusion / TTL self-healing / the cross-instance lattice — see `docs/Job-Global-Control-Gate-Design.md` §7's landing record). **All three defects are now fixed (2026-10-15).**

**A③ Closure (2026-10-15, patrol proxy decision, overturnable later)**: choose **keeping aligned checkpoints as the only consistent path**; unaligned is not scoped. Reasons: the only missing primitive is the per-partition effect fence (a correctness-critical path with 2PC interaction risk) while the benefit surface is narrow (perceptible only for long drain timeouts/high-throughput jobs). `RedisRuntimeConfig`'s unaligned switch is no longer needed (no feature to switch); P3 (the migration path) stays "not implemented". Restart condition: production workloads develop a real RPO need, at which point restart from a per-partition fence design batch — this sketch is not revived.

### Approach B: Full aligned barriers on both engines (Flink-style)

Async operator snapshots + barriers traveling with the record flow. Infeasible/uneconomical: the runtime has no operator queues (barriers have nowhere to live — riding record threads means returning to stop-the-world), in-memory state is an in-process mutable heap (async snapshots need COW across the whole store set), and Redis state snapshots are themselves cheap. Far more effort than ①+②; not recommended.

### Approach C: Delete `getCheckpointLock` (contract shrinkage)

Saves one misleading method, but loses ①'s natural attachment point and the user-side lock habit; `SourceContext` is a published SPI surface, so deletion is a breaking change with no offsetting benefit. Not recommended.

## Migration Path (Approach A, phased)

1. **P1 snapshot barrier** (landed 2026-10-11; see Approach A ①'s correction record): the coordinator's `checkpointLock()` + registered-store binding + lock-holding snapshot/restore aspects; 3 concurrency tests pin it, and backpressure scenarios are covered by the existing streaming tests (slow sink / 100k ordered records).
2. **P2 registration-surface generalization** (landed 2026-10-12): WatermarkState registered as a snapshot source via `registerSnapshotSource`; window accumulators registered per the operator-state lifecycle contract (2026-10-14; see Approach A ② and docs/InMemory-Operator-State-Lifecycle-Design.md).
3. **P3 unaligned v2**: **closed, not implemented** (the 2026-10-15 patrol proxy decision — the sketch's "epochs can align" premise does not hold; aligned checkpoints remain the only consistent path; restart conditions in A③'s closure above). The two-level CAS gate landed independently as its prerequisite (2026-10-14, `CheckpointGate`).
4. Documentation sync (landed 2026-10-11): `docs/checkpoint.md` gained the "in-memory snapshot/pipeline mutual exclusion" semantics (the two-lock contract); `docs/Deployment.md:97`'s stop-the-world record stays until P3 lands.
