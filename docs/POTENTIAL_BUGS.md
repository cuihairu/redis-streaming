## Critical

### B-01 The in-memory engine does not merge session windows: under SessionWindow every element becomes its own window [fixed]
- Location: `runtime/.../internal/InMemoryWindowedStream.java` (the drive bucketing logic); `window/.../assigners/SessionWindow.java:31-36`
- Trigger: `env.fromCollection(events).keyBy(k).window(SessionWindow.withGap(5min)).count()`, with events 1 minute apart.
- Impact: `SessionWindow.assignWindows` returns a `[ts, ts+gap)` window per element, the engine buckets exactly by start/end with no merge logic at all (`shouldMerge`/`TimeWindow.merge` have no callers repo-wide), so every element produces its own result (count=1). Session windows are entirely non-functional.
- Audit confidence: high
- Verification and fix: core's `WindowAssigner` gained a `supportsWindowMerging()` hook (false by default, with contract javadoc: the merge semantics and the trigger-state-discard limitation); `SessionWindow` declares support; `InMemoryWindowedStream` does a single merging pass over a key's intersecting buckets before bucketing (the invariant: a key's buckets are pairwise disjoint, so a single pass is complete — the proof is in the code comments). Regression tests in `InMemoryWindowedStreamSessionMergeTest`, 5 cases: consecutive events merge into one session [0,270)=4, a gap-exceeding interval splits, exactly the gap does not merge (half-open intervals), chain bridging merges [0,350)=5, multiple keys merge independently.

### B-02 StreamJoiner's match condition depends on arrival order: with an asymmetric JoinWindow whether a pair joins depends on who arrived first [fixed]
- Location: `join/.../StreamJoiner.java:54,68` (with `JoinWindow.java:74-77`)
- Trigger: `JoinWindow.afterOnly(10s)` (before=0). The right element R(ts=T+5) arrives before the left element L(ts=T): `processLeft` computes `contains(R.ts, L.ts)` → diff=L−R=−5s, and `-5 >= 0` is false → no match; had L arrived first, `processRight` computes `contains(L.ts, R.ts)` → +5s∈[0,10] → match.
- Impact: the join result depends on arrival order rather than the data. The two call sites' conditions are mirror images, so any asymmetric window breaks one side. INNER/LEFT/RIGHT/FULL_OUTER all fail silently.
- Audit confidence: high
- Verification: reproduced with `StreamJoinerOrderIndependenceTest` (5 of 6 cases failing on the old code: afterOnly/beforeOnly both ways + the of(3s,7s) boundary). Fix: `processLeft` changed to `contains(L.ts, R.ts)`, unifying both paths on the left-anchored predicate `R.ts − L.ts ∈ [−before, +after]` (matching the Kafka Streams semantics), plus an anchoring-contract javadoc on `JoinWindow.contains`. After the fix the join module's tests all pass.

### B-03 KGroupedTable.aggregate discards both the initial value and the accumulator: multi-row groups collapse to the last row [fixed]
- Location: `table/.../impl/InMemoryKGroupedTable.java:45-51`; `table/.../impl/RedisKGroupedTable.java:54-56`
- Trigger: `table.groupBy(...).aggregate(() -> 0L, (k, v) -> v)` aggregating 5 rows of one group.
- Impact: the adder's signature `BiFunction<K,V,VR>` cannot receive the current accumulator at all; `current = initializer.get()` is computed and immediately discarded. The result = `adder(key, the last row's value)` — any history-requiring aggregation (count/sum/reduce) is wrong.
- Audit confidence: high
- Verification and fix: the API changed to `aggregate(Supplier<VR> initializer, TableAggregator<K,V,VR> adder, TableAggregator<K,V,VR> subtractor)` (the new three-arg functional interface `TableAggregator` carries the accumulator). Both implementations became real folds; the InMemory version's tests had asserted the wrong "keep only the last row" behavior and now assert real sums (a=1+2=3, b=3+4=7, c=5).

### B-04 Consumer-side health reporting is entirely broken: the uniqueId and instanceId keys mismatch [fixed]
- Location: `registry/.../impl/RedisServiceConsumer.java:101-126,290-299,512-519`; `registry/.../health/HealthCheckManager.java:58,81,96-102`
- Trigger: enabling `enableHealthCheck=true` and discovering instances. `HealthCheckManager` keys its checkers by `getUniqueId()` (`"serviceName:instanceId"`) and passes it as the reporter callback's first argument; `reportHealthStatus` looks that value up in `discoveredInstances` (keyed by the bare `instanceId`).

Regression tests: `ConsumerHealthKeyTranslationTest` (the translation layer; 2/2 failing on the old code) + the integration test `ConsumerHealthEventIntegrationTest` (real Redis: an unreachable instance → a HEALTH_FAILURE event + `isInstanceHealthy("i1")`=false + checker count back to zero after unsubscribe; the old code received no events).

### B-05 Heartbeats are silently skipped when metrics collection is empty: instances expire during "normal heartbeats" [fixed]
- Location: `registry/.../impl/RedisServiceProvider.java:333-357`; `registry/.../metrics/MetricsCollectionManager.java:34-73,133-148`
- Trigger: a collection timeout (default 5s > the 3s heartbeat interval) / a collector failure / an empty enabledMetrics → `collectMetrics` returns an empty map → `NO_UPDATE`; with the default `enableMetadataChangeDetection=false` the result stays `NO_UPDATE` → no Redis write at all.
- Impact: under load peaks (exactly when heartbeats matter most) the ZSet score and the Hash TTL stop refreshing, and after `heartbeatTimeoutSeconds` the instance is evicted and consumers drop it. Only a TRACE-level log.
- Audit confidence: high
- Verification and fix: `HeartbeatStateManager` gained `shouldHeartbeatOnly(serviceName, instanceId)` (decided by the heartbeat interval); `processInstanceHeartbeat` routes empty collection results through that check instead of straight to `NO_UPDATE` — when due it produces `HEARTBEAT_ONLY`, and `executeUpdate`'s Lua path refreshes TTL/score as usual; when the heartbeat is not yet due it stays NO_UPDATE (no extra writes). Regression tests: `ProviderEmptyMetricsHeartbeatTest` (restoring the old short-circuit line reproduces 2/2 failures) and `HeartbeatStateManagerTest.testShouldHeartbeatOnlyDecidesByHeartbeatInterval`.
- Postscript (2026-10-12): provider-side metrics collection (the `registry.metrics` package) was removed wholesale; heartbeat decisions now have only the heartbeat/metadata tracks, and the "empty collection short-circuits the heartbeat" trigger surface no longer exists; `ProviderEmptyMetricsHeartbeatTest` was deleted with it, while `shouldHeartbeatOnly` remains as the heartbeat-interval decision primitive (`HeartbeatStateManagerTest.testShouldHeartbeatOnlyDecidesByHeartbeatInterval` still guards it).

### B-06 The config center's listeners are pub/sub-only with no resync: notifications missed during a disconnect are lost forever [fixed]
- Location: `config/.../impl/RedisConfigService.java:196-237,440-463`
- Trigger: a `publishConfig` while a subscriber's Redis connection flaps.
- Impact: listeners hold stale configuration until the next publish of the same dataId; no version reconciliation, no polling backstop. The registry consumer's event handling is likewise purely reactive.
- Audit confidence: high (a missing-semantics class)
- Verification and fix: a reconciliation poll was added: `ConfigServiceConfig.resyncIntervalMs` (default 30s, 0 disables) drives a fixed-delay daemon thread that re-reads each subscribed key's authoritative state (content+version in one readAllMap) and compares it against "the state the listener was last told" (the DeliveredState baseline), re-delivering on divergence — a missed notification goes from "lost forever" to "at most one interval late". The comparison is by content rather than version: content is the listener-visible state and necessarily converges to Redis's truth, while a version sequence spanning publishers' clocks may refuse to converge; a missing key counts as deleted (null content). When the baseline is undetermined (the addListener snapshot read failed), the current state is adopted silently without replay (subscribe-as-snapshot semantics). Delivery goes uniformly through `dispatchToListeners`, deduplicated idempotently on (content, version) — the reconciliation poll and an in-flight pub/sub delivery may both observe the same new published state (the poll can read after the Lua write but before event dispatch; empirically reproduced as [v1,v2,v2]), so the first delivers and the second no-ops, which doubles as a second line of defense for B-07's echo skip. The addListener snapshot baseline uses putIfAbsent (later subscribers do not reset an existing baseline). Poll exceptions catch Throwable (preventing a silent fixed-delay death, the B-08 lesson) and only warn before the next round; stop() shuts the scheduler and clears the baselines. The API only gains. The registry consumer is out of scope here: its event loss is backstopped by the discovery-cycle reconciliation (see B-45's fix).
- Regression tests: `ConfigResyncIntegrationTest` (@Tag("integration"), real Redis, interval=200ms, 4 cases: editing the Redis hash directly to simulate an undelivered publish is reconciled within a few intervals and delivered exactly once, a missed delete reconciles with null content, zero noise from polling when nothing is lost, and interval=0 disables fully back to purely reactive). Unit `ConfigResyncReconciliationTest`, 5 cases (mocks calling the package-private resyncSubscribedConfigs directly: re-delivers / does not double-deliver / deletes as null / silently adopts an undetermined baseline then must deliver on divergence / Redis exceptions swallowed + the scheduler starts and stops with configuration). Old-code reproduction: a temporary integration test failed on unfixed main with "listener is stuck at [v1]" (the reproduction test deleted per convention).

### B-07 Config change listeners receive two notifications per publish (local replay + the pub/sub echo) [fixed]
- Location: `config/.../impl/RedisConfigService.java:424-435`
- Trigger: any `publishConfig`/`removeConfig`: `topic.publish(evt)` followed by the synchronous `handleConfigChangeEvent(evt)`, with the message then looping back to the same JVM via the subscription.

### B-08 ClientHealthChecker spawns one non-daemon thread per instance and runs the first check synchronously on the calling thread [fixed]
- Location: `registry/.../health/ClientHealthChecker.java`; `HealthCheckManager.java`
- Trigger: enabling health checks and discovering N instances.
- Impact: the first `subscribe()/discover()` registration blocks per instance until the connect+read timeout (5s by default); un-stopped checkers (guaranteed by B-04) block JVM exit as non-daemon threads; thread count is O(instances).
- Audit confidence: high
- Verification and fix: three fixes at once — (1) the first check no longer inlines: `start()` becomes `scheduleWithFixedDelay(checkHealth, 0, ...)`, moving the first check onto the executor thread, so `registerServiceInstance` no longer blocks per instance until timeout (before the first check completes, `getLastHealthStatus()` defaults to true, matching the registry's registered-means-UP semantics); (2) threads become daemons: both the self-managed scheduler's and the shared pool's thread factories `setDaemon(true)`, so leaked checkers no longer block JVM exit; (3) a shared pool: `HealthCheckManager` lazily creates one `ScheduledThreadPoolExecutor` (core=max(2, cores/2), keepalive 60s + allowCoreThreadTimeOut, zero threads when idle), all instances' checks run on it via `ClientHealthChecker`'s package-private 6-arg constructor, and the public 5-arg constructor keeps a self-managed single-thread scheduler for backward compatibility; `stopAll()` closes the shared pool (subsequent registrations rebuild it). Also `checkHealth`'s catch widened from Exception to Throwable — an uncaught Error silently kills fixed-delay scheduling (no log, never checks again); caught, it still reports "check failed = unhealthy".
- Regression tests: `HealthCheckThreadingTest` (public API only, compiles against the old code) — the old code fails 3/3 as expected: the first-check thread = "Test worker" (inlined on the calling thread), the scheduler thread isDaemon=false, and check threads named "Test worker" (no shared pool); the new code passes 3/3. The existing `ClientHealthCheckerTest`/`CustomClientHealthCheckerCoverageTest` (including the stop-blocking probe's 5s-timeout path and the stop-interrupt path) all green, behavior-compatible.

### B-09 WindowedDeduplicator's "per-element time window" is really a set-level TTL refreshed on every write [fixed]
- Location: `reliability/.../deduplication/WindowedDeduplicator.java`
- Trigger: `windowDuration=1h` with continuous traffic; element "A" appears at t=0 and again a year later.
- Impact: entries never expire individually; the whole set's TTL is refreshed back to windowDuration on every `markAsSeen`, so under continuous traffic the set never expires → "A" still counts as a duplicate a year later; the set grows unboundedly, contrary to the "memory-bounded" documentation.
- Audit confidence: high
- Verification and fix: the data structure moved from a plain SET + whole-key TTL refresh to a ZSET (`RScoredSortedSet`, score = the element's last-seen time): `isDuplicate`/`checkAndMark` judge the window per element by score (`now - score < window`), writes `removeRangeByScore` to prune out-of-window entries and bound the set (≈ traffic rate × window), and a `window+60s` backstop TTL exists only to reclaim the whole key after traffic stops (no longer an expiry mechanism). The clock is injectable via a package-private constructor (`LongSupplier`; the public constructor defaults to `System::currentTimeMillis`); construction touches no Redis and gained NPE/IAE validation. The legacy plain-SET key migrates lazily on first access (getType==SET → readAll → delete → rewrite as a ZSET with the migration moment as last-seen, i.e. old members count as seen once more). The prune lower bound uses 0 rather than "-Infinity" (the latter does not survive Redisson's encoding portably).
- Regression tests: `WindowedDeduplicatorIntegrationTest` (public API only, compiles against the old code) — reproduces 2 failures on the old code: `elementExpiresWhileTrafficContinues` (a 300ms window; mark "A", then pump "B" at 50ms intervals for 700ms; `isDuplicate("A")` old=true (the whole-key TTL kept alive by traffic) / new=false ✓) and `legacyPlainSetIsMigratedToScoredLayout` (the key type old=SET/new=ZSET ✓); 2 more cases (idle expiry, the backstop TTL) pass on both as guards. Unit `WindowedDeduplicatorTest` rewritten with 9 cases (injected clock for window/prune boundary now−window/backstop TTL/migration/validation), and `DelegateCoverageTest`/`DeduplicatorsTest` migrated to the ZSET layout.

### B-10 PatternMatcher with allowEventReuse doubles active sequences per event: exponential blowup [fixed]
- Location: `cep/.../PatternMatcher.java:43-55,76-92`
- Trigger: `allowEventReuse(true)` with N consecutive matching events.
- Impact: the sequence count is 2^N (each event clones all active sequences and adds one) → OOM at ~30 events; time-window cleanup is the only relief, and a fast stream outpaces expiry.
- Audit confidence: high
- Verification and fix: the measured growth base is 2^(N+1)−2 (after newSeq joins, extendSequences extends it too), so 20 events yield 2,097,150 active sequences. Following B-20's precedent a retention cap was added: `DEFAULT_MAX_ACTIVE_SEQUENCES=1000` and a 2-arg constructor (negative → IAE; 0 disables extension tracking entirely); beyond the cap, oldest-first trimming (a batch subList removal, keeping the newest partial sequences — the ones most likely extended by later events), invoked after process()'s extension. Time-window cleanup stays; `process()`'s completed output is unaffected (each matching event still yields exactly one completed sequence). Trimming does not change the existing fact that "extension sequences are never emitted" — active sequences exist only for counting and extension, and with the cap memory is bounded at O(cap×maxSequenceLength).
- Regression tests: `PatternMatcherActiveSequenceCapTest` — old-code reproduction: a temporary old-API test (the 1-arg constructor) fed 20 events asserting ≤1000 measured 2,097,150 and was deleted after proving the failure. Six permanent cases: the default cap clamps exactly at 1000, an explicit cap=3 keeps the newest 3, cap=0 tracks nothing with completed output unchanged, negative → IAE, reuse disabled yields no partial sequences, and the time window still clears normally at full load.

### B-13 Checkpoint snapshots are typeless and versionless: LinkedHashMap/ClassCastException on the restore side [fixed]
- Location: `checkpoint/.../DefaultCheckpoint.java:65-93`; `RedisCheckpointStorage.java:37-48`; `RedisCheckpointCoordinator.java:184-188`
- Trigger: a POJO placed in the snapshot → a JSON-family codec stores and reads it → `getState` deserializes to `LinkedHashMap`.
- Impact: the unchecked cast `(T) stateMap.get(key)` blows up with a CCE only at the caller's first use; no schema/version field means state-class changes silently break old checkpoints; `restoreFromCheckpoint` only logs and restores nothing (presenting success while being a no-op).
- Audit confidence: high (a design class)
- Verification and fix:

  - Fix 2 (the snapshot version): `Checkpoint` gained `getSnapshotVersion()` defaulting to 0 (= legacy, unversioned); `DefaultCheckpoint` gained `CURRENT_SNAPSHOT_VERSION=1` and a `snapshotVersion` field — the field initializes to 0 so old JSON persisted before versioning faithfully reports legacy after deserialization, while the constructor stamps 1 on new instances; the round-trip was verified against real Redis (write 1 read 1, old payload reads 0).

- Regression tests: `DefaultCheckpointTest` (new instances are version 1; typed reads: same type/converted/null passthrough/impossible conversion errors; unmarked implementations read as legacy 0); `CheckpointSnapshotRoundTripIntegrationTest` (@Tag("integration"), real Redis: POJO+Integer-keyed Map round-trips faithfully, the snapshot version round-trips as 1, sink restore hands over 2 entries with correct content, unknown/incomplete checkpoints are refused with zero handover, and a legacy decoded shape converts back to the POJO via a typed read). The existing `CheckpointIntegrationTest` passes unchanged (the interface's new default methods are backward compatible).

### B-18 TopKAnalyzer ignores windowSize: the "windowed Top-K" is really an all-time Top-K [fixed]
- Location: `aggregation/.../analytics/TopKAnalyzer.java:24-31,52-70`
- Trigger: `createTopKAnalyzer(10, Duration.ofMinutes(5))` for a 5-minute rolling hot list.
- Impact: the `windowSize` field is never read; scores only grow and are trimmed only by rank (keeping 2k), never by time; entries falling out of the top-2k lose their scores forever → the window semantics are entirely wrong.

### RT-H3 Window/timer state is cleared before emit: a sink send failure permanently loses that window's accumulated data [fixed]
- Location: `runtime/.../redis/internal/RedisStreamBuilder.java` (the reduce/aggregate/apply/sum/count window emitters + `fireDueWindows`)
- Trigger: a window fire (the due zset entry already removed) followed by `sink.invoke` throwing (a Redis flap, a sink exception, a checkpoint abort).
- Impact: the messages enter RETRY redelivery, but the window state was already deleted in the `finally` → the redelivered elements re-accumulate alone and the window later fires with partial data — silently wrong results. apply is worse: the state clears before the buffered result is emitted.
- Verification and fix: two coordinated changes. (1) The five emitters' purge moved from `finally` to **after a successful emit** — an emit exception leaves the window state intact (apply likewise purges only after its whole buffered result delivers successfully, eliminating clear-then-send); (2) `fireDueWindows` `pollFirstEntry`s the member out of the due set before firing, and on a fire failure it re-queues the entry **at its original close score** — otherwise the window's elements were acked and no new element would ever re-add it to the due set, leaving the state present but forever unfireable. The semantic result: a sink failure no longer loses window data; redelivery delivers the complete window again (at-least-once may duplicate, consistent with the runtime's documented delivery semantics); true two-phase commit (an atomic emit+purge) remains the 2PC sinks' domain.
- Regression tests: `WindowFirePurgeAtomicityIntegrationTest` (count/apply cases: an armed-once sink throwing on the first close fire → asserting the complete window result (a count of 3) arriving via redelivery. Removal proof: on the old code the result set contains only the trigger record's own window's `[1]`, with the window's 3 permanently lost).

### RT-M3 Watermarks/window fires are purely message-driven: idle pipelines never fire and the capped remainder depends on later records [fixed]
- Location: `runtime/.../redis/internal/RedisPipelineRunner.java` (the idle flush + flush hooks) + `RedisStreamBuilder.java` (the windows' due-set flush hooks + the `markIdle/markActive` wiring) + `RedisRuntimeConfig.java` (`watermarkIdleTimeout`).
- Trigger: a silent source (an idle partition, a slow upstream, intermittent consumption backlog); or several keys' windows of one partition closing together with per-record fires capped by `windowMaxFiresPerRecord`.
- Impact: the watermark advances only at the message-processing chain's entry — a silent pipeline's due event-time timers and windows never fire (until a new record happens to arrive); after capping, the remaining due windows wait for the next record and are stranded forever without one; `markIdle()` is empty, so a `WatermarkGenerator` cannot declare the source idle.
- Verification and fix: three layers in concert. (1) **The idle flush** (configurable `watermarkIdleTimeout`, default null/ZERO off, negatives refused): the runner's timed sweep at min(timeout/10, 1s) detects silence (or `markIdle()` sets it) and flushes the watermark to `MAX_VALUE`, firing all due event-time timers; the next record opens a **new watermark epoch** via the `idleFlushed` flag (based on that record's event time), avoiding a watermark permanently pinned at the flush value. (2) **The windows' due-set flush hooks**: a window operator registers a one-shot flush hook with the runner at its first record (only when `watermarkIdleTimeout` is configured); the idle flush, after pushing the watermark to `MAX_VALUE`, walks each operator's known partitions, sets each partition ThreadLocal, and drains their due sets **without limit** — a silent pipeline's windows are thereby back-filled. Design trade-off: no event-time sweep timer as the bridge (timers are consumed at the end of the record whose watermark crosses the close score, before any flush, and a generation-gated re-arm would spin in `fireDueEventTimers`'s while loop re-registering duplicates); on the record path the due sets' sole owner remains the per-record drain, and trigger semantics (e.g. a defer-once close trigger) and the `windowMaxFiresPerRecord` cap are entirely unaffected by the flush, with the capped remainder waiting for the next record or the flush. (3) `markIdle()/markActive()` wire through `Context` to the runner's idle flag (`markIdle` needs `watermarkIdleTimeout` configured to have a sweep to trigger). The semantic result: an idle pipeline's windows/timers back-fill after the timeout (at-least-once unchanged, possibly duplicating with late data); within a post-flush new epoch, late old elements still follow the late-drop policy.
- Regression tests: `RedisPipelineRunnerIdleFlushTest` (mock-free, 4 cases: a silent flush fires a far-future timer, the post-flush new-epoch watermark = the next record's event time rather than MAX, `markIdle` flushes without silence, and unconfigured stays purely record-driven) + `IdleWatermarkWindowFlushIntegrationTest` (real Redis: a silent pipeline's window back-fills `contains(2L)` after timeout; with `windowMaxFiresPerRecord=2` the flush hook drains the remainder — the element total 11 is the invariant guarding against cross-window splits (4 keys accumulating 10 + the trigger record z's own window 1; the flush watermark being `MAX_VALUE`, z's window back-fills too); removal proof: disabling the hook loop yields `got [1, 2, 1, 2, 4]` and `got []` respectively).

### RT-M4 State restore deletes before building: a mid-flight failure both loses state and silently continues stateless [fixed]
- Location: `runtime/.../redis/internal/RedisRuntimeCheckpointManager.java` (`restoreState`) + `RedisStreamExecutionEnvironment.java` (the startup restore path).
- Trigger: any single-key rebuild failing during restore (a Redis flap, a timeout, one key's operation erroring).
- Impact: the old implementation deleted all live keys first and rebuilt key by key, swallowing single-key failures at debug → keys present in the snapshot but failing to rebuild silently vanish, and the job continues on partial (even empty) state with wrong aggregation/dedup results and no alarm.
- Verification and fix: two coordinated changes. (1) Restore became a **two-phase stage-then-RENAME** — all snapshot keys are first written under `<finalKey>:rst:<checkpointId>` staging names (a pre-delete keeps retries idempotent), and once staging completes each key RENAMEs atomically into place (key-level atomic, overwriting any type); any staging or swap failure → clean the staging keys and throw IllegalStateException, with the live state never deleted first; snapshot keys with empty data are deleted after their swap succeeds (restored as empty), and keys outside the snapshot are cleaned only after all staged keys land; when the snapshot index/schema has no entry the corresponding live key is **deleted rather than RENAMEd** (RENAMEnx on a missing staging key errors directly in Redis — caught by the real-Redis integration test, invisible to mocks); TTL is retention policy rather than correctness, warning only on failure. (2) `restoreFromLatestCheckpointOrNull`'s semantics changed: when a restore was explicitly requested and a checkpoint exists, a restore failure throws IllegalStateException (aborting env startup) instead of silently degrading to a stateless start; no checkpoint still returns null for a normal fresh start; a checkpoint belonging to another job (a meta jobName mismatch) still returns null — adopting another job's checkpoint is wrong, and a fresh start for this job is the correct result, not a restore failure.
